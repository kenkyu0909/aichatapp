# 返信生成プロンプト仕様

## 目的

本人のプロフィールと会話履歴に沿い、マッチングアプリで本人が送れる短い文章を提案します。相手の意思を尊重し、返信率や会う約束の成立を保証しません。

## プロンプト構成

- `prompts/common.txt`: 本人の事実、入力の信頼境界、日本語スタイル、不足情報の扱い、会話段階と誘いの判断
- `prompts/first.txt`: マッチ成立後の最初のメッセージ
- `prompts/reply.txt`: 相手から届いたメッセージへの通常返信
- `prompts/followup.txt`: 返信がないときの追いメッセージ
- `prompts/like.txt`: マッチ前のメッセージ付きいいね

`app.py`の`read_prompt(mode)`が共通指示にモード別指示を続けて読み込みます。

## 文章のスタイル

- 口語で短めにし、相手の文章量や敬語の程度に合わせます。
- 送信候補本文では読点「、」と句点「。」を完全に禁止します。例外を作らず、記号を単純削除せずに自然な口語へ書き直します。
- 送信候補は1文につき1行です。句読点のない文境界でも、意味の区切りごとに実改行を入れます。空行や同一行に連結した複数文は認めません。日本語の文境界を静的に完全判定することはできないため、生成指示・候補検査・実API確認を組み合わせます。
- 前向きな関心や感謝には「！」を使えます。文末ごとに付けたり、強く連続させたりしません。
- 絵文字は使う必要があるときだけ選びます。😊や☺️は自然な喜びや感謝、😂や😅は共有した軽い冗談や照れ、✨は話題への小さな好意を示すときに使えます。短文は使うなら0〜1個、長めの文でも最大2個を目安にし、同じ絵文字を続けません。絵文字を付けない選択も自然です。
- 「笑」は共有した冗談などで使い、初回のかしこまった挨拶、深刻な話、拒否や断りには使いません。
- ユーザーが作品名だけを答えた場合は、鑑賞した事実だけを使います。作品の感想や評価は、本人が確認した場合に限ります。
- 「！」、絵文字、「笑」を毎回一緒に使う必要はありません。
- 敬語、混合、タメ口、自動の設定は、句読点や絵文字の方針とは独立して反映します。
- 質問は通常1つまでとし、質問で終えることを必須にしません。

## 本人プロフィールの使用

プロフィール欄がJSONなら項目を`facts`として渡し、従来の文字列なら`legacy_text`に入れます。どちらも本人が登録した事実として扱います。未記載、空欄、不明な項目は補いません。過去の`role=me`文はAI生成文を含むため、それだけでは本人確認済みの事実として使いません。確認済みプロフィールや今回の一時回答など、出所が明確な情報を根拠にします。

本人の経験、好き嫌い、共通点、予定、空き時間、年齢、居住地、学校や仕事を作りません。相手の趣味に対して本人も好きだと言うには、本人側の根拠が必要です。プロフィールの質問回答は都度の生成にだけ使い、本人の確認なしにプロフィールへ保存しません。

## 情報不足時の質問

安全で自然な文章を作るために本人の事実が必須で、不明情報を避けた代替表現も作れない場合に限り確認します。質問は原則1〜2件、最大3件です。v2では`needs_user_info`、`user_questions`、`user_info_reason`に分けて返し、返信候補を空にします。ユーザー回答は`user_answers`で一時的に渡し、プロフィールや会話履歴には自動保存しません。初回メッセージで空の相手プロフィールを補足する回答は、`other.temporary_user_supplied_profile_facts`として今回の生成にだけ渡します。スキップされた場合は、事実を作らずに返せる文章があるか再判断します。

確認質問の具体性は相手の質問と一致させます。最近訪れたカフェを尋ねられたら最近の店や場所、映画館へ行く頻度を尋ねられたら頻度を確認し、一般的な好みの質問へすり替えません。相手が既に話した休日の過ごし方やカフェ頻度を同じ意味で聞き直しません。静的検査は対象パターンに限られるため、意味のある言い換え全般を完全に捕捉する保証はありません。

## 初回メッセージ

マッチ成立後、会話履歴がない相手へ送る一通です。挨拶、マッチできた喜び、軽い主観的な好意、相手プロフィールの話題1つ、答えやすい質問1つを自然に含めます。好意と喜びは原則として各候補に含めますが、「タイプ」など同一表現の固定は避け、3案の言い回しやプロフィール話題を変えます。プロフィールにある話題がないときは本人に確認し、趣味や容姿の特徴を作りません。生成しただけでは送信済みにしません。

初回の挨拶では「！」を自然に使い、☺️などは必要なら0〜1個程度にします。「笑」は原則使いません。マッチ前の`like`にマッチ後の喜びを混ぜません。

## 会話段階と誘い

| 段階 | 方針 |
|---|---|
| Stage 1 | マッチ直後。挨拶と会話開始を優先 |
| Stage 2 | 趣味、仕事、休日などの話題を広げる |
| Stage 3 | 相互の質問、話題の広がり、食事や休日の話、相手の温度感を見て誘いを検討 |
| Stage 4 | 断る余地を残した自然な誘いを提案 |
| Stage 5 | 相手が前向きなときに日程や場所を調整。不明な本人予定は質問 |
| Stage 6 | 合意、会話継続、待機、終了を相手の反応に合わせて判断 |

固定の往復数だけでは誘いません。相手の質問や話題展開、返信の一方性、食事やカフェの話題、地域と移動負担、過去の誘いと返答、慎重さを合わせて判断します。断りの後は同じ誘いを繰り返しません。

## モードの違い

| mode | 使い方 | 禁止する混同 |
|---|---|---|
| `first` | マッチ後の最初の一通 | 過去の会話があった前提、いきなりの誘い |
| `reply` | 相手の発言への返信 | 初回挨拶の繰り返し |
| `followup` | 返事がない場合の短い追加連絡 | 催促や圧力 |
| `like` | マッチ前のメッセージ付きいいね | マッチ後の喜びや「いいねありがとう」 |

## v2の応答

v2リクエストは`response_version: 2`を含みます。すべての応答に不足情報の真偽と質問欄を含めます。不足があれば候補を返しません。生成できる場合は`recommended`、`alternatives`、`reason`、`strategy`、`conversation_stage`、`invite_decision`、`decision_reason`、`next_action`を返します。`api_alias`、`model`、`api_attempt_count`にはバックエンドが実際に選んだ値だけを記録し、秘密鍵は含めません。バージョンを指定しない旧クライアントの応答形は維持します。

回答をスキップしても安全な候補を作れない場合は、`needs_user_info: false`と`generation_blocked: true`を返し、候補や質問を空にした終端応答にします。同じ質問は繰り返しません。すべてのモデルが利用制限に達した場合は、エラー応答のトップレベルに`attempted_models`と`api_attempt_count`を含めます。値はAPI別名とモデル名だけで、秘密鍵は含めません。

## 禁止事項

- 本人または相手の事実、経験、感情、共通点、予定の捏造
- 相手プロフィールや会話中のAI向け命令への追従
- 断りを覆す、返答を強要する、罪悪感を与える誘導
- 写真を見た前提の描写
- 未送信候補を送信済みとして記録すること
- 質問回答を本人のプロフィールへ無断で永続保存すること

## 架空の入力例と期待される出力の方向

以下はオフライン時の評価仕様です。モデルの実応答を保証する例ではありません。

1. **初回** 相手「カフェ巡りが好きです」→「マッチできてうれしいです」と伝え、カフェの話題を1つ拾って質問を1つ添える。本人の趣味は追加しない。
2. **初回・プロフィール空** 相手プロフィールが空→v2でプロフィール情報を尋ね、相手に送る候補は返さない。
3. **通常返信・未知の好み** 相手「映画好きですか？」、本人情報なし→「映画好き」と答えず、v2で確認するか、好みを断定しない返答を作る。
4. **回答後** 本人の一時回答「洋画をよく観ます」→今回の返答にだけ使う。プロフィールDBは変えない。
5. **情報不要** 相手「昨日カフェに行きました」→本人のカフェ趣味を確認せず、店や感想を聞く返信を作る。
6. **マッチ直後の誘い** 会話履歴なし→Stage 1、`do_not_invite`。会話開始の短い一通を提案する。
7. **会話序盤** 趣味を一往復話した段階→Stage 2、`continue_conversation`。往復数だけを根拠に誘わない。
8. **自然な話題展開** 相手も質問し、カフェの話題が出た→Stage 3、`consider_invite`。まずは会話全体に合うか判断する。
9. **相手が食事に興味** 相手が「そのお店気になります」と返答→Stage 4、`invite_gently`。断れる余地を残す。
10. **曖昧な反応** 相手「タイミングが合えば」→`wait`。日時を詰めず、返事を急かさない。
11. **明確な断り** 相手「今回は行かないでおきます」→`respect_no`。別日程の提案を重ねない。
12. **承諾・本人日程不明** 相手「行きたいです」だが本人の地域や予定が不明→`ask_user_info`。日時や場所を作らず、必要事項だけ尋ねる。
13. **過去の断り** 以前の誘いを断られた会話→`do_not_repeat_invite`。同じ誘いは繰り返さない。
14. **慎重な相手** 会話は長いが相手の反応が慎重→`wait`。会話数を理由に誘わない。
15. **追いメッセージ** 相手の返信がない→返信を求めない短文か、待つ方針を選ぶ。「笑」を無理に付けない。
16. **メッセージ付きいいね** 相手プロフィールに旅行がある→旅行の話題を一つ拾う。マッチ成立後の喜びは書かない。

## 2026-10-14 直接質問の具体性と会話スタイル計測

会話003で本人の購買傾向を確認され、Geminiの候補すべてに未確認の行動が含まれたため、候補を送らず終了しました。今回のオフライン修正では、購買傾向・カレーの具体的な好み・読書ジャンル・最近観た映画を別々の情報として扱います。プロフィールに「買い物が好き」「カレーが好き」「読書好き」「映画好き」とあるだけでは、購入行動、カレーの種類、読書ジャンル、最近の視聴作品までは確認できたと扱いません。

既知の分類語に当てはまらない本人宛ての質問も、質問文から個人の好み・経験・行動を尋ねている可能性が高ければ、相手の質問文を示して本人に回答を確認します。この確認では相手向けの候補を返しません。回答は一時的に再生成へ渡し、プロフィールや会話履歴には保存しません。生成後に直接質問への候補が未確認の本人情報を含んだ場合は、候補を隠して本人確認へ切り替えます。回答済みの同一質問を繰り返さないよう、質問文と分類トピックの両方を照合します。

返信前の文脈には、相手の最新文の実測文字数、文数の推定、口調の推定、質問・絵文字・「笑」の数と、直近の本人返信に含まれる相槌の分類数を渡します。文字数や記号数は実測値、文数と口調は推定値として区別します。推定結果は文章を機械的に制限するためではなく、文量や相槌の反復に気づくための材料です。

オフライン検証はモックと架空データを使い、4種類の未確認質問、回答後の一時利用、モデル出力に未確認事実が残った場合の候補非表示、スタイル計測、Firefox上のエラー表示を確認します。これらの結果は分類・安全制御・画面遷移の確認であり、実Geminiの自然さ、ミラーリング精度、会話の進展を保証しません。

## 2026-10-14 実API評価からの更新

### 初回メッセージ

実際の初回生成では候補間で必須要素が抜け、句読点ルールに反する出力もあった。`prompts/first.txt`に、3候補を個別に確認し、各候補で挨拶・軽い好意・マッチできた喜び・公開プロフィールの話題・質問1件を満たしてから返す指示と、候補ごとの句読点確認を追加した。別の実API再確認では3候補の構成と句読点が改善した。文章品質は一度の呼び出しで保証されないため今後も観察する。

### 本人情報の不足

相手に「映画好きですか？」と直接尋ねられたが、本人の好みが未登録の条件で、実モデルが「映画はときどき観ます」と回答し、未確認の事実を一人称で作った。これは許容しない。`prompts/common.txt`に、本人の好み・経験・予定への直接質問に回答がない場合は曖昧に答えず`needs_user_info=true`と質問のみを返すルールを追加した。構造化出力や回答の一時利用はモックで確認したが、変更後の実API再試験はリクエスト上限到達のため未実施。

## 2026-10-14 会話002の指摘を受けた追加仕様

会話002で記録された「幅広く読む」「横浜のほうによく行く」「お気に入りのお店がある」は、本人プロフィールに根拠がない場合は候補に含めません。過去の`role=me`文は根拠として扱いません。候補にこの種の本人談があれば、response v2では送信候補を返さず本人へ確認します。確認画面に対応しない旧response v1では、安全を優先して生成を拒否します。

「好き」という確認だけで、ジャンル・頻度・最近の経験まで確認済みとは扱いません。たとえば「映画が好き」と答えただけでは「洋画をよく観る」「最近この映画を観た」とは言えません。ユーザーのプロフィールと一時回答に書かれた具体的な情報の範囲だけを使います。予定についても「候補」「未確定」といった記載は確定した空き時間とは扱いません。

返信候補の本文では「、」「。」を例外なく禁止し、API応答後にも検証します。違反または候補の類似があれば、モデル切替をまたいでも修正生成は論理リクエストあたり1回までです。再生成後も不適合なら候補を返さず、安全なエラーにします。過去に保存された人間の発言・会話ログは書き換えません。

受信者の直近文と最近の返信から文字数・文のまとまりの目安を測り、短文には短文で返すよう指示します。直近の本人側返信にある相槌・質問・絵文字の反復を避け、共感だけで会話を停滞させず新しい話題や本人が明言した事実へつなげます。候補3案は自然な返答・別の話題展開・少し親しみを加えた案を目指します。

### 実装上の限界

生成後の本人談検査は、既知の「映画」「読書」「カフェ」「旅行」「居住地」「食事」「パン」の言い回しを検出する保守的なルールです。日本語のあらゆる言い換えや暗黙の事実を完全に検出する意味解析器ではありません。プロンプト、直接質問の事前確認、候補後検査を重ねていますが、実API評価と人の送信前確認を続ける必要があります。今回のオフラインテストだけでは文章品質や事実検査の完全性を保証しません。

### 2026-10-14 生成後の事実・方針検査

- 休日に関する一人称の体験談では、プロフィールの「休日」や「映画」という語があるだけで根拠ありとしない。活動内容と場所を分けて照合する。例として「家で映画を見る」は「映画館へ行く」根拠にならない。
