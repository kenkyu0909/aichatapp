# 実Gemini品質確認003の人手評価

## 実行条件

架空プロフィール・会話と新規の一時SQLiteを使い、既存FastAPIの`/api/generate`経由で実際のGeminiを呼び出した。旧APIキーやユーザーデータは使っていない。API別名はAPI1、モデルは`gemini-3.5-flash-lite`。キー文字列は記録していない。

初回確認は9論理要求・10プロバイダー試行、続く限定追試は5論理要求・8試行、回答後と誘いケースの再確認は2論理要求・4試行だった。合計16論理要求、22プロバイダー試行。すべてAPI1/3.5で、429・モデル切替・他モデル使用はなかった。課金状態・残り枠・実費は確認していない。

## 観察結果

### 本人情報不足（T77）

初回では未登録の映画好みについて質問したが、回答後も同趣旨の追加確認を返し候補を出せなかった。再確認では、架空回答「映画好きです。特に洋画をよく観ます」を渡すと2試行後に3候補が返り、洋画への好みを勝手に補わず、プロフィール回答に沿った話題を返した。再確認の候補は句読点禁止を守り、短い会話として読めた。T77の修正後実API結果はPASSとする。初回の失敗は`quality_checks_003.json`に残す。

### 短文・複数文・落ち着いた話題

Aでは短い相手発言に対し短めの候補が3つ返った。本人プロフィールにあるカフェ趣味の範囲で返した案は使える。一方、他の候補には未確認の店の好みを補ったものが混じるため、候補を人が選ぶ必要がある。

Bでは候補ごとにコーヒーの好みや、落ち着いた店を探す趣味など、本人プロフィールにない自己開示が含まれた。第三案は相手の話題を尋ねており比較的安全だった。3案の構造が返っただけでは品質PASSにできず、T93全体のFAIL要因として扱う。

Cでは落ち着いた短文に対して短い候補が返ったが、1候補が「最近は全然観れてない」と本人の未確認の視聴状況を述べた。事実検査へこの型を追加し、オフライン回帰テストで検出を確認した。生成した他の候補に句読点はなかった。

### 誘いの判断（G）

相手がカフェに関心を示したケースで、方針と本文の不一致が2回続き、バックエンドはHTTP 502 `invalid_response`として候補を拒否した。これは外部のクォータ・通信障害ではなく、モデルの方針整合性エラーである。相手の拒否や慎重さに反して誘いを送ることは防げたが、自然な誘いを安定して出せることは確認できていない。T93はFAILのまま扱う。

## 制限

各ケースの候補は少数の一回実行で、自然さ・個人事実の全表現を保証できない。日本語の事実検査は既知の型を確認するルールで、一般的な意味解析ではない。特に候補本文の本人談は、実送信前の人による確認が必要である。
