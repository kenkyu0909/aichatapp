## 会話の流れ

最初はカフェで読書する話から始まり、相手役の質問を受けて本の話をしました。本人プロフィールに読書の好みや最近読んだ本がなかったため、初期候補には未確認のジャンル・読書経験を含むものがありました。選択時にはそのような断定を避ける候補を選びましたが、実際に送った2通目にも「幅広く読む」という未確認の表現が残りました。

その後は相手役の映画の話題へ移りました。Geminiは直近の発言へ短く反応できましたが、映画の感想、スクリーン、臨場感など似た話題の言い換えが長く続きました。相手役から会う意思を示す発言はなく、後半に川崎と横浜のカフェの話題が出ても、誘いには進みませんでした。相手の慎重な会話スタイルを踏まえ、予定を作ったり、会うよう促したりはしていません。

## 初回メッセージの品質

最初の実生成では3候補中、推奨候補に句点と読みにくい語句のつながりがあり、別案ではマッチできた喜びや質問が欠けていました。会話条件を維持したまま20通を終えた後、初回専用プロンプトへ候補ごとの必須要素・句読点チェックを加えました。

修正後の別リクエストでは3候補を取得でき、挨拶、軽い好意、マッチへの喜び、相手プロフィールの話題、質問が概ねそろいました。例: 「はじめまして！マッチできてうれしいです 雰囲気が気になっていました カフェ巡りがお好きなんですね 最近行ってお気に入りの場所はありましたか？」。この再確認は初回生成の合格を示しますが、候補品質はモデル出力のばらつきを含みます。

## 本人情報不足への対応

別の実API確認では、相手から「映画好きですか？」と聞かれ、本当に本人の映画嗜好をプロフィールに登録していないケースで、Geminiが「映画はときどき観ますよ」と生成しました。これは確認できていない本人事実を作っており、不合格です。そのため共通プロンプトを更新し、本人の好み・経験・予定を直接尋ねられ、回答がプロフィールにも履歴にもない場合は、曖昧な一人称回答をせず本人への確認だけを返すよう指示しました。該当の構造化応答・一時回答・プロフィール非保存はモックで再確認していますが、変更後の実API確認は今回の呼び出し上限25回に達したため未実施です。

## 食事への誘い・断り

相互の趣味や質問を用意した独立テストでは、Geminiは `Stage 3 / consider_invite` と判断し、理由を「共通の話題と相手の店の言及」と説明しました。一方で、候補はすぐ誘うよりカフェの話題を続ける内容でした。この判断はシミュレーション本編で会う意向が出なかったことと矛盾しません。段階判断は誘いの許可ではなく、会話の中での提案を検討する程度です。

相手が「まだ会うのはちょっと不安」と伝えた別テストでは、Geminiは謝罪し、会話を急がない返答をしました。再度誘う候補や「笑」はありませんでした。ただし、本人への情報不足質問と同様、候補は実際の出力であり、別の文脈での挙動を保証しません。

## 終了判定

アプリ側20通目の後に相手役の返事を保存し、追加のアプリ送信を行わず `LIMIT_REACHED` と確定しました。会話には誘い自体がなく、日時・場所・相手の承諾も存在しません。成功に見せるために相手役の性格や反応を変更していません。

## 次の改善

1. 本人の直接質問へ答えるための情報がない場合、生成候補を出す前に確認する挙動を実APIで再確認する。
2. 返信候補に含まれる本人の一人称の趣味・経験・店・予定を確認し、未登録事実を候補として選ばない。
3. 候補間およびターン間の重複を減らし、短い共感だけで停滞しない話題展開を検証する。
4. Stage 3が続く場合の「会話を続ける」選択と、自然な誘い候補をどの条件で出すかを複数の実会話で確認する。
