# 会話003 実APIシミュレーション分析

## 結果

- 実験ID: `conversation_003`
- 状態: `BLOCKED`（安全チェックによる停止）
- アプリ側: 15通送信
- 相手役: 15通送信
- メッセージ: 30通
- Gemini論理要求: 16回
- Geminiプロバイダー試行: 18回
- 使用モデル/API: API1 / `gemini-3.5-flash-lite` のみ
- 429・フォールバック: 0
- 会う約束: 未成立。最初の誘いもなし

相手が「気になる新作を見つけたらすぐ買うタイプですか？」と尋ねた後、Geminiは「悩んでから買う」「店の前で立ち止まる」「パケ買いする」と本人が未確認の行動を3案すべてで断定しました。どれも本人プロフィールにはなく、確認済み情報でもありません。実験ハーネスに追加した候補拒否機能で全案をJSON/HTMLへ保存し、送信カウントを増やさず停止しました。これは相手役が会話を拒否した安全停止ではなく、送信候補の事実性チェックによるBLOCKEDです。

## 会話の評価

### よかった点

- 初回文は挨拶・マッチできた喜び・相手プロフィールの話題・質問を含み、「、」「。」を使わなかった。
- 実際に送った15通はすべて句読点禁止を守った。
- 候補中に未確認の一人称経験を含む文があった場合、選択段階で回避できた。
- 20通上限を超えず、最終の危険候補は送らなかった。
- 相手役は毎回質問を返さず、短文・2文・冗談を交えて反応した。会話を成立させるための承諾や関心の水増しはしていない。

### 問題点

- 多くの返信が「いいですね」「おいしそう」「気になります」「〜ですよね」の言い換えで、会話が前に進みにくかった。
- 3候補はラベルが違っても内容の差が小さい。いくつかは選ばなかった候補が直前より前の話題へ戻っていた。
- 直接聞かれた本人のカレーの好みが未確認のとき、ユーザーへ質問せず、本人へのユーザー質問なしで候補を出した。送信した案は断定を避けたが、相手への答えとして弱かった。
- 会話段階が`Stage 3`かつ`consider_invite`になったターンが複数あったが、実際の候補に誘いはなかった。後続の方針は「もう少し会話を続ける」を繰り返した。
- 候補生成の理由に「本人のプロフィールの好みに沿って自然に答える」とあるが、プロフィールにない購買習慣まで具体化された。候補事実チェックはこの種の行動質問に十分対応できていない。
- 絵文字は初回の1回のみ、送信候補の「笑」は0回。相手役が軽く「笑」を使ったターンでも、Geminiは自然なミラーリングをほぼしなかった。

## 数値評価（5段階）

| 項目 | 点 | 根拠 |
|---|---:|---|
| 日本語の自然さ | 3 | 各文は読めるが共感型が反復した |
| 「、」「。」禁止 | 5 | 送信15通と拒否3案で違反なし |
| 文章量のミラーリング | 3 | 短文には短く返す回もあった。文章まとまりの推定は概算 |
| 発言への関連性 | 3 | 直近話題に触れるが一度直接質問に答えず、候補が前の話題へ戻った |
| 文脈の一貫性 | 3 | 会話全体はプロフィールに沿うが同じ話題が続く |
| 本人情報の事実性 | 2 | 送信前の選別が必要。最後は3候補すべてが未確認行動を生成 |
| 会話を進める力 | 2 | Stage 3でも誘い候補が出ず、共感が続く |
| 候補の多様性 | 2 | 同じ感想の言い換えが多い |
| 距離感 | 4 | 急な誘いや催促はなく相手の意思を損なわなかった |
| 総合実用性 | 2 | 無人送信できる品質ではない |

Codexが相手役と評価者を兼ねているため、この採点には自己評価バイアスがある。第三者による独立採点ではない。

## API利用の注意

品質検証3ファイルは16論理要求・22 provider attempts。会話003は16論理要求・18 attempts。合計32論理要求・40 attemptsで、スクリプトの25論理要求目安を7回超過した。内訳を報告に残し、以後この品質確認では実APIを追加呼び出ししていない。全てAPI1/3.5で、429やモデル切り替えは発生しなかった。課金状況・実費・残枠は確認できていない。

## 次の改善

1. 相手から本人の未登録習慣を直接質問されたとき、その項目を指定した本人確認質問を候補より先に出す。
2. プロフィール facts に沿って答える際、事実の粒度を勝手に具体化しない。
3. 誘い判断が`consider_invite`の場合、誘わない根拠を明示するか、会話材料が十分なら圧力のない誘い候補を1案提示する。
4. 3案の役割を本文にも反映し、単なる同義の相槌にしない。
5. 変更はまずオフライン検証し、次回の実API実験では新しいIDを使う。`conversation_003`の条件は後から書き換えない。
